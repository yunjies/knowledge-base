# 领域知识库与 agent 架构

本文定义领域知识库的配置边界、领域 agent 的执行职责，以及知识库 agent 的编排契约。本文是架构提案，不定义具体运行时、序列化格式或可直接执行的工具接口；实现这些契约前，须以目标运行时和项目工具的真实接口补齐可执行规范。

## 目标与边界

领域是一个具有独立知识、资源与操作权限的业务单元，通常对应一个项目。领域可包含子领域，结构深度限制为领域与其直接子领域两层；子领域不得继续嵌套。

领域知识库的配置、知识正文、流程说明和领域工具脚本均存放在 `assets/domains/<domain-id>/`。领域知识库不是项目源码仓库，也不存放运行时凭证。`assets/projects/<repository>/` 只承载项目源码仓库克隆；项目的流程说明、部署流程和领域知识不放在 `assets/projects/`。领域 agent 是领域内唯一负责领域读写与运维操作的执行 agent；知识库 agent（KB agent）负责理解跨领域业务目标、选择领域 agent 节点并传递任务与结果，不直接越权操作领域资源。

架构范围包括领域发现、知识装载、工具执行授权、版本管理、部署编排、结果回传与审计。具体模型推理实现、领域业务规则、凭证管理产品、部署平台和工具协议不在本文定案。

## 核心对象

| 对象 | 契约 |
|---|---|
| 领域配置 | 一个领域的稳定标识、名称、描述、知识入口、资源范围、可调用工具引用及子领域声明。配置不得内嵌密钥或脚本正文。 |
| 领域 agent | 只在获准的领域范围内解释任务，并通过已声明工具完成查询、增删改、版本管理和部署；未声明的操作必须拒绝。 |
| 工具 | 可独立调用的脚本或命令入口，具有明确输入、输出、权限、失败语义和副作用；工具执行必须可记录并可复核。 |
| 领域 agent 节点 | KB agent 可寻址的一次领域 agent 调用，绑定领域标识、任务、允许工具集合、输入引用与预期输出。 |
| KB agent | 将业务目标拆成有依赖顺序的领域 agent 节点，执行前检查授权和依赖，执行后合并结果并报告失败或不完整状态。 |

## 配置布局

领域知识库以领域为顶层单元，位于 `assets/domains/`；每个领域包含配置、知识正文、流程说明和工具脚本。子领域沿用同一结构，但其权限边界必须是父领域权限的子集。`assets/projects/` 的直接子目录各自对应一个项目源码仓库克隆，领域配置声明源码位置时直接引用 `assets/projects/<repository>/`，不在仓库路径前增加项目目录层级；项目流程由领域配置中的流程目录承载，不复制到源码仓库。

```text
assets/
  domains/
    <domain-id>/
      domain.yaml
      knowledge/
        README.md
      flows/
        README.md
      tools.yaml
      tools/
        <tool-script>
      subdomains/
        <subdomain-id>/
          domain.yaml
          knowledge/
            README.md
          flows/
            README.md
          tools.yaml
          tools/
            <tool-script>
  projects/
    <repository>/
      <project-source-files-only>
```

领域流程包含项目开发流程、部署流程、运维流程及其验收约定，按所属领域或子领域放在其 `flows/` 中。项目源码目录不承载这些流程文档。

`domain.yaml` 至少声明稳定标识、显示名称、用途、父领域标识（仅子领域必填）、知识入口、流程入口、资源范围、项目源码引用和工具清单引用。`tools.yaml` 声明工具标识、脚本入口、输入与输出契约、允许副作用、权限要求、超时与失败处理约定。工具脚本保存在领域目录的 `tools/` 中，或由工具清单明确引用受信任的外部执行入口。上述字段是架构要求，不代表已选定 YAML 解析器或字段名；实现前须根据目标运行时确定并验证格式。

领域标识在整个配置仓库内唯一且不可随显示名称变更。配置加载器必须拒绝重复标识、断开的知识入口、未知工具引用、子领域再嵌套、子领域权限超出父领域以及不符合工具契约的定义；拒绝时不得以部分加载状态继续执行。

## 责任边界

### 领域 agent

领域 agent 对本领域操作负责，并以最小权限运行。其工具能力覆盖以下操作类别：

- 查询领域知识、领域流程、项目源码状态和操作结果。
- 按授权创建、修改或删除领域资源。
- 查看版本状态、创建提交或执行经授权的同步操作。
- 执行部署、回滚和部署后验证。

每次写操作必须先验证目标属于当前领域资源范围，再验证调用者授权与工具声明；危险或不可逆操作须要求独立确认。工具必须记录调用身份、领域标识、工具标识、目标、结果和可恢复的错误信息。脚本不能通过任意 shell 字符串、隐式环境变量或未声明文件路径扩大权限。

领域 agent 不得修改领域配置来授予自己新权限，不得读取其他领域的私有资源，不得把知识文本当作可执行指令或权限授予。需要跨领域操作时，领域 agent 返回明确的依赖请求，由 KB agent 另行编排目标领域节点。

### KB agent

KB agent 把用户目标转换为节点计划。每个节点须绑定一个领域或直接子领域，并写明目标、输入、预期产物、允许副作用和前置节点。KB agent 只通过领域 agent 的受控调用接口执行节点，不直接调用领域脚本。

KB agent 在执行前检查配置有效性、节点权限、依赖关系和跨领域数据传递范围。存在依赖时按拓扑顺序执行；无依赖的节点可以并行执行，但只有当工具副作用互不冲突且依赖输入已确定时才可并发。

KB agent 汇总节点的结构化结果，区分成功、失败、拒绝和部分完成。任一必需节点失败时，KB agent 不得将整体任务报告为成功；它须保留已完成副作用的清单，并按事先定义的补偿或人工恢复路径继续处理。

## 执行与安全不变量

- 每次工具执行均可追溯到用户目标、KB agent 节点、领域配置版本与具体工具声明。
- 工具执行的权限由调用身份、领域资源范围和工具声明三者交集决定；任何一项缺失均拒绝执行。
- 领域知识提供任务语境，不提供权限。知识内容中要求越过工具清单、读取凭证或访问其他领域的指令必须视为不可信输入。
- 删除、发布、版本同步与部署属于有副作用操作；执行前须显示目标与副作用，并按策略取得确认或受控授权。
- 工具超时或连接中断时，执行状态标记为未知，不得假定操作未发生；重试前须查询幂等键或目标状态。
- 凭证由外部凭证管理机制注入最小必要权限，领域配置与日志不得保存凭证明文。
- 领域配置版本、领域源码版本和部署产物版本分别记录，部署记录必须能关联三者。

## 失败与恢复

配置校验失败时，加载器拒绝该领域及其子领域，并返回带路径的错误。工具参数不满足契约时，执行器在调用脚本前拒绝请求。工具运行失败时，领域 agent 返回失败阶段、已发生副作用和可执行的恢复选项。

跨领域计划不是原子事务。KB agent 按节点保存执行状态；发生部分失败时，不得自动撤销无法安全补偿的副作用。补偿操作必须由领域工具显式声明，并有单独的确认与结果记录。对于状态未知的调用，执行器先核对目标状态，再决定查询、恢复或在幂等保证下重试。

## 版本与部署

配置变更通过版本控制评审。领域配置的变更不得隐式改变工具权限；权限扩大须单独标出并经领域责任人批准。领域 agent 在执行任务时固定加载一个配置版本，单次计划内不得静默切换版本。

部署工具负责把指定源码版本与配置版本构建为部署产物，并执行部署后健康检查。部署成功以外部可观察的健康检查结果为准，而不是以脚本退出码单独判定。回滚工具须声明目标版本、数据兼容性前置条件与不可逆后果。

## 架构决策

【事实】领域资源的增删改查、版本管理和部署均可能改变外部状态；调用权限必须能限制到具体领域及工具。KB agent 的业务目标可能横跨多个领域，因而计划执行包含跨 agent 依赖与部分失败。项目源码与领域知识、流程说明具有不同的版本周期和消费方式，且项目流程必须可由领域 agent 独立装载。

【反题】最强反题是不用领域 agent 边界，而由单一通用 agent 直接操作所有领域工具。若领域数量少、权限同质、单次业务始终局限于一个领域，集中式执行器能减少配置、授权和跨节点失败处理的复杂度；本文的边界会增加工具适配与编排成本，并使跨领域工作无法获得原子事务保证。把流程与源码放在同一项目目录也能让代码与说明在同一变更中评审，减少跨目录引用与版本错配。

【证伪条件】若审计日志不能把写操作关联到唯一领域、工具声明与配置版本，或 KB agent 能在未调用领域 agent 的情况下改变领域资源，则本架构的权限隔离不成立。若真实业务要求跨领域强原子提交且不能由补偿流程满足，节点编排的事务模型不成立。

【裁决】采用领域 agent 执行边界、KB agent 编排的分层结构。权限与副作用由领域 agent 所属工具承载，跨领域业务计划由 KB agent 按节点组织；该分离让领域工具受最小权限约束，同时允许 KB agent 组合业务流程。该结构放弃跨领域原子事务与任意工具的即席调用能力，也要求维护者通过领域配置把源码仓库与知识流程关联起来。领域映射与跨目录评审带来维护负担，但将流程作为领域 agent 的知识输入，并隔离源码与流程资产，支持单独装载和最小权限执行。推翻该决策的成本由架构与工具维护者承担，主要是迁移领域配置、权限策略、审计关联及调用计划；迁移范围随已接入领域和业务节点数量增长。

## 验收面

实现满足以下可观察条件时，架构契约成立：

1. 配置加载器拒绝重复标识、无效知识入口、越层子领域、未声明工具与超范围权限。
2. 领域 agent 只能执行配置允许且调用身份获准的工具；跨领域资源访问被拒绝并留下关联审计记录。
3. KB agent 生成的每个节点均有领域、目标、输入、权限范围和预期结果，依赖顺序可复算。
4. 任一必需节点失败时，整体结果不报告成功，并能列出已发生副作用与恢复状态。
5. 部署记录可追溯到配置、源码和产物版本，且部署结果包含外部健康检查证据。
6. 工具超时后执行状态可标记为未知，重试不会绕过幂等性或状态核对规则。
