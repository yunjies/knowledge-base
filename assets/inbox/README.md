# 需求收件箱

本目录承载**尚未完成的需求**：一条需求进来说明它要什么，本目录把这条需求拆解成执行流程，并让流程中每个节点当前处于什么状态可以直接读出。需求做完后，本目录不再承载它——文档整篇移入 [assets/archive/](../archive/README.md) 归档，这里不留「已完成」式的存档。

## 文件命名规则

一个文件一条需求，文件名是四段式，以点分隔：

```
req.<修改的项目>.<简述内容>.<时间戳>.md
```

- **`req`**：固定前缀，标明这是一条需求而非笔记或项目流程。
- **`<修改的项目>`**：本需求实际修改的项目名，取小写英文短名（如 `home-media-pilot`、`knowledge-base`），不含点、空格与斜杠；若改的是知识库自身，使用 `knowledge-base`。
- **`<简述内容>`**：对本需求产出的简短英文 slug，取小写英文短名（如 `browser-screenshot`、`inbox-naming`），不含点、空格与斜杠；只概括内容，不重复项目名。
- **`<时间戳>`**：需求**投递进本目录的时刻**，精确到秒，形态为 `YYYYMMDD-HHMMSS`。语义是到达顺序而非推进顺序，故一条需求在流程推进中**不改名**——文件名不变，变的是它内部节点的状态；需要按投递顺序查看时按该末段时间戳排序，不把文件名的自然字典序误读为投递顺序。
- **`.md`**：需求文档是流程类文档，受[流程类文档撰写规范](../../.agents/skills/process-doc-writing/reference/process-doc-writing-constraints.md)约束。

取投递时刻的命令与判据：`date +%Y%m%d-%H%M%S`。

## 新建一份需求：从骨架开始

新需求**复制 [template.md](template.md) 改名**，不从头写。骨架文件名固定为 `template.md`，故它不参与命名规则的判定（它不叫 `req.*`），也不参与「每份需求都须有前置块」的判定——它本身就是按该形态写好的可填充版。

复制后按顺序填三处：

1. **改名**为 `req.<修改的项目>.<简述内容>.<时间戳>.md`，项目与内容使用小写英文 slug，时间取复制时的投递时刻。
2. **填前置块**的三个键，删掉尖括号占位。留着一个未填的占位值不会静默通过——判据把「值仍是 `<...>`」判为未填，故复制后忘记改会在守护上报红。
3. **裁剪主图**：骨架里的节点是通用形态，按本需求实际的分叉点增删；用不上的节点连同它的章节整段删除，不要留空壳。没有阻塞可能就删掉 `BLOCKED` 及其虚线出边。

骨架的节点标识符取英文短码（`START`、`DEVELOP`、`TEST_GATE`…），尖括号只用在**描述名与参数说明**里，不用于标识符——标识符要匹配 `^[A-Z][A-Z0-9_]*$`，写中文或尖括号会判违规。

### 骨架的四个阶段

骨架的主干是四个**阶段**，按「改代码 → 证明改对了 → 把既成事实落档 → 核对改的正是要的」排列。每个阶段在主图里是一个子流程蓝图型节点，阶段内部做什么画在它自己的章节里。

| 阶段 | 产出 | 判据 |
| --- | --- | --- |
| 开发 | 功能改动本身 | 改动未越出 `target` 边界 |
| 测试 | 覆盖本需求行为的用例与运行结果 | 全绿且退出码为 0 |
| 归档 | 落档后的文档 | 文档描述的流程与改动指向同一事实 |
| 验收 | 逐条对应关系 | 需求要求的都做了，且没有需求外的东西 |

**每个阶段起一个独立 subagent**：四个阶段各自由一个**新起的** subagent 执行，彼此不共享上下文，只通过主图上的参数交接。这样分的理由是每个阶段要独立判断上一阶段的产物——开发者自证改动正确、或验收者参与过开发，都会用自己当初的思路去核对，看不到自己的偏差。阶段边界（该阶段做什么、不做什么）写在各自的章节标题下。

**测试失败回开发、验收不通过回开发**：这两条是主图上的回边。各自只在**判阶段**的节点上分叉，回到 `DEVELOP` 重做并重跑后续阶段；测试阶段不改产品代码，验收阶段也不自己动手修正——判据与被判对象同出一处，绿灯就失去意义。

**验收通过不等于归档**：验收通过后必须把结果交给需求方，只有收到需求方明确同意，才允许把需求文档移入 `assets/archive/`；未回复、口头推定或自动流程均不得触发归档。

## 前置数据块

每份需求文档在**主流程图之前**先给一个 YAML 前置块，用结构化的键值把这份需求的引用关系定死：它针对知识库的哪一部分、产出会落在哪里、原始需求从哪来。流程图画的是「怎么做」，这个块写的是「做的是谁、做完放哪」——后者是引用关系，不是步骤，故不画进图里，而以机器可读的形态落在图前。

块的形态是一段 `yaml` 围栏，是**本文档 H1 之后的首个内容块**，键名固定为下面这组：

```yaml
target: 这份需求改的是知识库的哪一部分
output: 这份需求的产出落在哪里
prompt:
  - 原始需求的一句原话
  - 又一句原话
```

- **`target`**：这份需求针对的既有内容，写**取回路径**而非描述——具体到目录、文件或章节。判据是读者能据它一步定位到被改的对象；若该需求新增内容而非改动既有内容，写它将落进的父目录。
- **`output`**：达成之后的产出落在哪。与 `target` 的区别在于二者在流程的两端：`target` 是入口处被动的东西，`output` 是出口处新生成或改写后的东西；两者常指向同一路径（原地改写），此时两处都写该路径，不写「同上」。
- **`prompt`**：这条需求的原始提示词留档——一个条目一段**对话原话**，按提出顺序排列，头一条是需求最初被提出的那句提示词。需求在对话中被提出、被追加、被更正，每次变动都**追加**一个条目，已有的条目**不得改写或删除**：被改写过的留档不再是原始提示词，凭据的价值正来自它未经修改。故该列表的长度即这条需求的演进次数，而**最后一条是当前有效的需求陈述**，前面的条目记的是它如何被更正到这一步。

### 前置块位置与本目录对 P-01 的放宽

[流程类文档撰写规范](../../.agents/skills/process-doc-writing/reference/process-doc-writing-constraints.md) 的 P-01 要求 H1 之后的首个内容块是陈述目标的自然段落，P-02 要求首个 h2 章节内只有主流程图，P-10 要求 H1 与首个 h2 之间的内容块至多一个。三条同时成立时，**图前不存在合法的块位**——前置块放在目标段之前会顶掉 P-01 的首块地位，放在目标段与首个 h2 之间会超出 P-10 的至多一个，放进首个 h2 则撞 P-02。

本目录的裁决是**局部放宽 P-01**：前置块取 H1 之后的首个内容块，目标段紧随其后。理由是本块的键值形态（`target`／`output`／`prompt`）使读者在读流程之前先知道改的是谁、产出放哪，这个次序优先于「先读一段散文」；且 P-01 与 P-10 在其它流程文档中的功能——把目标段摆在一个好读的位置——在本目录仍由紧随其后的目标段承担。

放宽的范围**只限本目录**：`assets/projects/*/feature-flow.md` 与判据册样张仍按 P-01 的原样判定。`_lint` 的 F01 门禁据此识别两种开头形态——通用文档取自然段，本目录的文档取 YAML 前置块后紧跟自然段。

### `prompt` 与「正文不采纳会话视角」的关系

本文档的正文遵守[文档撰写规范](../../.agents/skills/doc-writing/reference/doc-writing-constraints.md)的 D-05——正文不出现只有该次会话参与者才能解析的坐标，读者不访问会话记录也能读懂流程。`prompt` 块是这条规则**唯一的、被显式划定的例外**：它的功能正是留档会话本身，故它按定义带会话坐标。

这个例外的边界因此必须写死：

- **`prompt` 里只放对话原话**，不放流程结论、不放推导、不放决策理由——那些归正文与各节点章节。
- **正文不得引用 `prompt` 的条目**，不得写「按 `prompt` 里说的办」这类指向块的表述；正文须独立可读（D-03 同理）。`prompt` 是存档，不是正文的注脚。
- **条目内的原话照抄，不作润色**，包括口语与错别字——润色后的转述不再是凭据。

## 节点状态与配色

本目录的流程文档，其流程图中每个节点都带**状态**，由颜色区分：

| 颜色 | 状态 | 含义 |
| --- | --- | --- |
| 黄色 | 待执行 | 尚未开始，或已开始但还没拿到结果 |
| 绿色 | 已执行 | 已完成，且结果经证据确认 |
| 红色 | 阻塞 | 卡住，需要外部协助才能继续 |

配色以 mermaid 的 `classDef` 与 `class` 承载，取色值不取自渲染器默认值——默认值随渲染器主题变化，那样颜色就不承载状态了。三档取色的具体值、以及「经证据确认」如何判定，见每份需求文档自己的「状态配色」章节：那是该文档与其读者之间的契约，本 README 只规定三档状态与三档颜色的对应关系。

**状态是节点的一个属性，不是文档的一个属性**——同一张图内三档颜色可以并存，这正是这张图要传达的信息。

## 什么进这里

- **尚未完成的需求**：有明确目标、且达成目标需要多步、需要一个可被他人读到的执行流程。判据是这条需求**是否还需要有人接着推进**。

## 什么不进这里

- **已完成的需求**：需求做完后，流程文档整篇移入 [assets/archive/](../archive/README.md)，其结论该归哪归哪——落成项目的归 `assets/projects/<项目>/feature-flow.md`，落成规范的归 `_meta/` 或随 skill 分发的判据册，跨会话仍成立且无处可放的归 `assets/notes/`。本目录不留「已完成」式的存档：一份状态全绿的残留文档，与一份真的待办在目录列表里长得一样，它会让收件箱的实际待办量不可读。
- **单个项目的已实现流程**：归 `assets/projects/<项目>/feature-flow.md`。一条需求**做完之后**其流程归那里；**在做期间**它归本目录，因为此时它还不是该项目的既成事实。
- **能从工程自行取回的事实**：取值、清单、命令输出、目录结构。写取回路径，不写取值（判据见 [_meta/agent-constraints.md](../../_meta/agent-constraints.md)）。
- **执行规范**：约束 agent 应当如何行动的条目归对应规范册。本目录只承载需求，不承载规范。

## 与 `assets/notes/` 的分界

两者都可能由一次任务产生，分界是**这条信息还有没有待办**：`assets/notes/` 放的是**做完之后仍然成立**的结论，本目录放的是**还没做完**的流程。一条需求做完，它的结论按上面「什么不进这里」归位，流程文档本身移入 `assets/archive/`——是移动不是复制，收件箱承载的是进行中的过程，需求结束时它必须离开本目录。
