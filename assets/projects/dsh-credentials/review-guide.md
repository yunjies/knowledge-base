# dsh-credentials 工程评审说明

本文说明如何对 dsh-credentials 源码开展多维度独立评审，并将每个经证据确认的问题转化为经过反证测试的修复记录。评审者在评审阶段仅能读取仓库 `src/` 下的代码；其他工作阶段按其任务读取必要材料。本说明定义的是评审办法，不是实际评审报告。

## 范围与执行护栏

评审对象为 `assets/projects/dsh-credentials/dsh-credentials/src/` 下的实现。评审阶段不得读取 `src/` 之外的代码、测试、README、文档、配置、构建产物、提交记录或外部资料，也不得运行会读取这些对象的工具。评审者不得修改源码或测试。

每个评审步骤必须交给一个全新的一次性 subagent。不同步骤之间不共享上下文，只交接本说明规定的结果；不得由同一 subagent 连续完成评审、测试、修复、验收或报告归档。不同评审维度也由各自独立的 subagent 执行，并可并行开展。

问题必须是可从源码定位的事实，包含触发条件、可观察的错误结果与预期行为。推测、风格偏好和无法验证的担忧不得登记为问题。每项事实必须有测试证据；缺少覆盖时先补测试，不得跳过失败验证直接修复。

## 评审维度

每个维度的 subagent 只读取 `src/` 中与该维度相关的代码，不读取测试或项目外资料，不运行测试或命令。至少分别覆盖以下维度：

- 输入校验与错误处理路径。
- 状态与数据一致性。
- 并发、资源释放与生命周期。
- 敏感信息处理与权限边界。
- 客户端交互状态与可见行为。
- 宿主端口、适配器与协议行为。

每个评审者独立提交候选事实、源码位置、触发条件、可观察结果和预期行为，并提出能区分正确与错误行为的测试断言。汇总者由另一名一次性 subagent 担任；它按根因去重，并只读取候选项引用的 `src/` 位置核实证据。无法从源码说明错误行为的候选项不进入事实清单。

## 每项问题的测试与修复闭环

对每项保留的事实单独执行以下闭环。每个阶段均由独立的一次性 subagent 负责：

1. **建立红色测试**：测试 subagent 检查是否已有直接覆盖该事实的测试；没有时新增测试。测试阶段可以读取编写和运行测试所需的测试文件、测试说明与配置，但不得从这些材料另行推导问题事实。测试须在修复前因目标错误行为而失败；环境故障、语法错误或无关断言失败不算证据。
2. **修复问题**：新的修复 subagent 按事实修复源码，不得删除、跳过或弱化证据测试，也不得夹带无关改动。
3. **确认绿色**：另一名测试 subagent 运行事实对应测试及适用的相关测试集合。命令须退出码为 0，且不得通过跳过测试、删除用例或放宽断言取得绿灯。失败时返回修复阶段，保留失败证据。
4. **破坏性反证**：新的 subagent 在本地临时工作区受控地撤销或破坏对应修复，再运行该事实的测试；测试必须因目标断言失败而转红。破坏前记录可精确恢复的工作区状态与恢复步骤。不得提交、推送、部署、触及生产环境或破坏无法准确恢复的内容；无法保证恢复时停止并报告阻塞。
5. **恢复与复测**：由另一名 subagent 撤销所有破坏性改动，确认工作区恢复至修复后的状态，并再次运行相关测试确认全绿。未恢复或复测失败时不得归档，须先恢复正确状态并重新验证。

测试阶段需要读取的运行入口与命令，以项目自身测试说明为准；记录实际使用的命令、退出码和可区分目标失败与环境失败的输出证据。

## 报告与事实落档

评审报告放在项目仓库根目录新增的 `reviews/` 文件夹中，文件名采用 `review-<timestamp>.md`。每个事实只在修复前红、修复后绿、破坏后红、恢复后绿四类证据齐备后登记。未经完整闭环的候选项不得混入已验证事实；可在报告的未验证面中记录其状态与原因。

每条事实使用以下结构化字段：

```yaml
factId: <唯一的事实标识符>
note: <事实、触发条件与可观察错误结果>
category: <问题所属的评审维度>
testpath: <证明该事实的测试文件路径>
evidence: <修复前失败、修复后通过、破坏后失败、恢复后通过的可复算证据>
solution: <修复行为及对应源码位置>
```

报告还应给出测试运行入口、修复与测试的对应关系、破坏方式与恢复核验，以及没有证据覆盖的范围。报告不得把无法复现的判断描述成事实。
