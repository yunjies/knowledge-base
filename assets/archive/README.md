# 已完成或取消需求归档

本目录承载**已完成或明确取消的需求**：完成需求须验收通过并获需求方明确同意；取消需求须由需求方明确取消并到达文档所载的取消终态。符合其中一条后，流程文档才从 `assets/inbox/` 整篇移动到本目录。本 README 规定这里放什么、不放什么、归档的动作形态，以及归档后的知识库提交与发布要求。

## 什么进这里

- **验收通过且获准归档，或经需求方明确取消的需求文档**：原 `assets/inbox/req.<修改的项目>.<简述内容>.<时间戳>.md` 的整篇。完成需求须走完验收阶段并获需求方明确同意；取消需求须在流程图中有明确的取消终态，且该终态记录需求方的取消决定。未完成且未取消的需求仍归 `assets/inbox/`。
- **归档动作是移动，不是复制**：`assets/inbox/` 那边必须删去。两处同时存在同一份文档，等于给同一条需求制造了两个状态面，后来者无法凭目录判断它到底有没有做完。

## 什么不进这里

- **尚未完成且未取消的需求**：归 `assets/inbox/`。本目录的文件不再推进；一份带黄红节点且没有取消终态的文档出现在本目录，说明归档动作在验收之前发生，须移回 `assets/inbox/`。明确取消的文档按下文取消态归档规则处理。
- **需求的结论摘要**：结论按各自归属落位——属某个项目的知识、流程或部署说明归该项目所属的 `assets/domains/<领域>/`，落成规范的归 `knowledge-repository/` 或随 skill 分发的判据册，跨会话仍成立且无处可放的归 `assets/notes/`。本目录留的是**过程留档**（当初的需求原话与推进路径），不是结论的副本。
- **来历叙事之外的整理**：不为归档文件另写索引或清单——目录列表本身即按投递顺序排列的档案。

## 归档的形态

- 文件名保持 `req.<修改的项目>.<简述内容>.<时间戳>.md` 原样，不改名。`<时间戳>` 段是**投递时刻**，记录的是这条需求进入收件箱的时刻，不是它完成的时刻；改名会让归档后的文件与它在 `prompt` 留档里的履历脱节。
- 完成态归档前，完成流程图不得包含未执行的取消节点或未走过的取消分支，且所有节点状态均须标为已执行（绿色）。只有需求方实际取消需求时，取消态流程图才加入可达的 `CANCELLED` 终端；归档前将该终端标为已执行（绿色），其余节点保留真实状态，不得伪标为绿色。流程文档的形态与配色契约由 [assets/inbox/README.md](../inbox/README.md) 规定，归档文件仍受那份契约约束。
- **状态范围**：归档文档中的节点记录需求流程到本地移动归档为止；移动后的 GitHub 提交与推送是知识库发布步骤，不写成归档文档的节点状态，也不在移动后改写归档文档。
- **过程记录分支与 PR base**：每个 `assets/inbox/req.*` 与 `assets/archive/req.*` 文件都是单条过程记录，不属于知识库 `main`；该记录从创建、推进到归档，始终留在需求方明确确认的非 `main` 记录／内容分支。项目专属需求使用需求方明确确认的该项目内容分支；知识库范围的方法需求须另行确认非 `main` 的知识库记录分支，不能从项目分支推定。未确认适用分支时停止，不得以 `main`、默认分支或当前分支替代，也不得自动切换分支。归档移动不得改变记录所在分支。项目内容 PR 的 base 必须是已确认的项目内容分支；知识库通用方法可另以 PR 发布到 `main`，该 PR 不得捆绑任何单条需求记录。归档到已确认内容分支前，刷新该分支对应的远端引用并审查待发布提交；若分支有未审核或未授权提交，暂停并向需求方确认，不自行切换或重置。步骤见[需求收件箱 README](../inbox/README.md)。
- **最小发布范围**：只暂存本次获准归档需求文档、对应领域知识库的流程文档更新及明确授权的文件，不夹带其他用户修改。通用方法 PR 只含通用方法文件，不含活动或已归档的单条过程记录。归档前满足上文对应的绿色节点要求；推送与远端确认按[版本管理 skill](../../.agents/skills/version-management/SKILL.md)办理。
