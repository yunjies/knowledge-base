# 已完成需求归档

本目录承载**已完成的需求**：一条需求验收通过且需求方明确同意归档后，它的流程文档才从 `assets/inbox/` 整篇移动到本目录。本 README 只规定这里放什么、不放什么、以及归档的动作形态。

## 什么进这里

- **需求方同意归档的需求文档**：原 `assets/inbox/req.<修改的项目>.<简述内容>.<时间戳>.md` 的整篇，内容不在移动时改写。判据是该需求已在 `assets/inbox/` 的流程里走完验收阶段——未完成的需求归 `assets/inbox/`，本目录不承载待办。
- **归档动作是移动，不是复制**：`assets/inbox/` 那边必须删去。两处同时存在同一份文档，等于给同一条需求制造了两个状态面，后来者无法凭目录判断它到底有没有做完。

## 什么不进这里

- **尚未完成的需求**：归 `assets/inbox/`。本目录的文件不再标注状态、不再推进——一份带黄红节点的文档出现在本目录，说明归档动作在验收之前发生，须移回 `assets/inbox/`。
- **需求的结论摘要**：结论按各自归属落位——属某个项目的归 `assets/projects/<项目>/feature-flow.md`，落成规范的归 `_meta/` 或随 skill 分发的判据册，跨会话仍成立且无处可放的归 `assets/notes/`。本目录留的是**过程留档**（当初的需求原话与推进路径），不是结论的副本。
- **来历叙事之外的整理**：不为归档文件另写索引或清单——目录列表本身即按投递顺序排列的档案。

## 归档的形态

- 文件名保持 `req.<修改的项目>.<简述内容>.<时间戳>.md` 原样，不改名。`<时间戳>` 段是**投递时刻**，记录的是这条需求进入收件箱的时刻，不是它完成的时刻；改名会让归档后的文件与它在 `prompt` 留档里的履历脱节。
- 归档前把节点状态全部标为已执行（绿色），使文档在归档时呈终态；除此之外不改写内容。流程文档的形态与配色契约由 [assets/inbox/README.md](../inbox/README.md) 规定，归档文件仍受那份契约约束——它描述的是这类文档怎么写，不因文档搬家而换判据。
