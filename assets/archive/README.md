# 已完成或取消需求归档

本目录承载**已完成或明确取消的需求**：完成需求须验收通过并获需求方明确同意；取消需求须由需求方明确取消并到达文档所载的取消终态。符合其中一条后，流程文档才从 `assets/inbox/` 整篇移动到本目录。本 README 规定这里放什么、不放什么、归档的动作形态，以及归档后的知识库提交与发布要求。

## 什么进这里

- **验收通过且获准归档，或经需求方明确取消的需求文档**：原 `assets/inbox/req.<修改的项目>.<简述内容>.<时间戳>.md` 的整篇。完成需求须走完验收阶段并获需求方明确同意；取消需求须在流程图中有明确的取消终态，且该终态记录需求方的取消决定。未完成且未取消的需求仍归 `assets/inbox/`。
- **归档动作是移动，不是复制**：`assets/inbox/` 那边必须删去。两处同时存在同一份文档，等于给同一条需求制造了两个状态面，后来者无法凭目录判断它到底有没有做完。

## 什么不进这里

- **尚未完成且未取消的需求**：归 `assets/inbox/`。本目录的文件不再推进；一份带黄红节点且没有取消终态的文档出现在本目录，说明归档动作在验收之前发生，须移回 `assets/inbox/`。明确取消的文档按下文取消态归档规则处理。
- **需求的结论摘要**：结论按各自归属落位——属某个项目的归 `assets/projects/<项目>/feature-flow.md`，落成规范的归 `_meta/` 或随 skill 分发的判据册，跨会话仍成立且无处可放的归 `assets/notes/`。本目录留的是**过程留档**（当初的需求原话与推进路径），不是结论的副本。
- **来历叙事之外的整理**：不为归档文件另写索引或清单——目录列表本身即按投递顺序排列的档案。

## 归档的形态

- 文件名保持 `req.<修改的项目>.<简述内容>.<时间戳>.md` 原样，不改名。`<时间戳>` 段是**投递时刻**，记录的是这条需求进入收件箱的时刻，不是它完成的时刻；改名会让归档后的文件与它在 `prompt` 留档里的履历脱节。
- 完成态归档前把节点状态全部标为已执行（绿色）。取消态归档前把取消终态标为已执行（绿色），其余节点保留真实状态；不得把未执行节点伪标为已完成。流程文档的形态与配色契约由 [assets/inbox/README.md](../inbox/README.md) 规定，归档文件仍受那份契约约束。
- **状态范围**：归档文档中的节点记录需求流程到本地移动归档为止；移动后的 GitHub 提交与推送是知识库发布步骤，不写成归档文档的节点状态，也不在移动后改写归档文档。
- **发布完成条件**：归档前先确认知识库根仓库当前分支为 `main`，刷新 `origin/main` 并审查全部待推送提交；若分支错误或有未审核、未授权提交，暂停并向需求方确认，不自行切换或重置。前置检查通过后移动归档文档。**文档移动完成后**，只暂存本次归档文档、对应项目的 `feature-flow.md` 更新及明确授权的流程文件，不夹带其他用户修改；提交并推送知识库 `main`，刷新远端引用并确认远端包含本次提交。只有远端核实成功知识库归档发布才完成；推送失败须报告并续办。步骤见[需求收件箱 README](../inbox/README.md)。
